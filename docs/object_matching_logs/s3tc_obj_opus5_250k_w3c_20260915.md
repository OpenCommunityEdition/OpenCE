## 1. `_RGBToColor` + `_DecodeBlockRGB` - the w1 reopen re-verified, with the mechanism proved from the bytes

`scratch/workers/s3tc/reopen_rgbtocolor.c` (current real file plus the Microsoft/S3 reference `RGBToColor` body) re-gates
at HEAD to `== exact 14 residual 4 unwritten 0`, guard passed: `_RGBToColor` 96/0 and `_DecodeBlockRGB` 448/2 both strict
EXACT (**+544 padded bytes**), zero sibling loss, and `_DecodeBlockRGB__single_pixel` improves from `[size,relocs,sha]` to
`[sha]` only.

This wave re-derived the mechanism instead of restating it. January's frame is `push ecx` - ONE four-byte slot at
`[ebp-4]`:

```
 4  xor ecx,ecx            ; rgb zero-extended
 6  mov cx,word [eax]
 9  mov dl,cl / shl dl,3 / push ebx / mov bl,dl / shr bl,5 / or dl,bl     ; B
16  mov dword [ebp-4],ecx  ; 32-bit store of the zero-extended word  -> byte 3 := 0
19  shr word [ebp-4],5     ; 16-bit shift of the same slot
1e  mov eax,[ebp-4]        ; last dword read of rgb
21  mov cl,byte [ebp-4]    ; last byte read of rgb
27  mov byte [ebp-4],dl    ; colour store 0 - the slot changes owner here
37  mov byte [ebp-3],cl
41  mov byte [ebp-2],al
44  mov edx,[ebp-4]        ; *pcolor = color   (byte 3 is the zero from offset 0x16)
```

`word rgb` and `struct s3tc_color color` have disjoint live ranges, so VC7 merges them into one slot; the alpha byte is
never stored and is deterministically zero. **No source form with the alpha initialised can be exact**: an initialiser
costs at least one extra store and, decisively, makes `color` live from entry, which destroys the merge (our current
`= { 0 }` body homes `color` at `[ebp-8]` with `sub esp,8`, 90 code bytes vs January's 81). This is a policy question only.

The blocker is unchanged: the reference body never assigns `color.rgba[3]` before `*pcolor = color`, which WORKER_BRIEF
section 5 classifies under "uninitialized reads", and the 2026-09-07 park says "do not restore the original indeterminate
alpha read to regain bytes". Premise refutation offered for the owner: every January consumer overwrites or ignores that
byte (`_DecodeBlockRGB` and the single-pixel decoder store 0xFF/0 into the palette alpha immediately after the calls;
`_Quantize` passes the colour only to `ColorToFcolor`, which reads channels 0..2); the read is part of a whole-aggregate
copy; and the emitted code provably writes zero there.

`_DecodeBlockRGB` needs **no body change at all**: its `[size]`+`[relocs]` tags are an inline boundary, not a tie -
January inlines the first `RGBToColor` call into the dead `source` parameter slot and calls the second out of line
(2 relocations, not 3), and that decision is a property of the helper body.

## 2. `_EncodeBlockRGBColorKey` - the 448-byte structural gap is solved, with no artificial width

w1 found that our projection (min/max) loop is unrolled 8x2 while January's is a plain 16-trip loop, and attributed it to
"a constant-trip `for` loop whose induction variable is `short`/`byte` is not unrolled", refusing to propose it because
there is no provenance for a narrow variable.

**WORKER_BRIEF section 9 already carries the right law and it was never applied here: VC7 13.00.9254 unrolls a small
constant-trip `for`/`while` but NOT a `do`-`while`.** Spelling only the projection loop as

```c
	min = 99999.0f;
	max = -99999.0f;
	bit = 1;
	i = 0;
	do
	{
		if (wAlpha & bit)
		{
			t = (...) / len2;
			if (t < min) { min = t; }
			if (t > max) { max = t; }
		}
		bit <<= 1;
		++i;
	}
	while (i < S3TC_BLOCK_PIXELS);
```

removes the unroll: `e1.c` (real file + do-while only) goes **2640 -> 2208**. The accumulation spellings w1 tried are
confirmed inert (`e2.c` 2640 with the `for`; `e3.c` byte-identical to `e1.c`).

The residual 16 bytes are an **aggregate home**, per the frame-size-gap law plus "a dead slot is an elided aggregate
member". January's frame is `sub esp,0x1a8`, ours `sub esp,0x198`. Decoding January's frame from the operands:
`fcolors[16]` at -0x1a8 (256 B), a 3x3 matrix, `upper` at -0x84, the other 3x3 matrix, `lower` at -0x50, then **36 bytes
of scalars at [-0x40..-0x1d]** with `x` at -0x3c, `y` at -0x38, `z` at -0x34 and a never-referenced slot at -0x30, then
`mean` at -0x1c, `len2` at -0xc, `min` at -8, `t` at -4 = 424 = 0x1a8. Ours has only 20 bytes in that region. Writing the
principal axis as `struct s3tc_fcolor direction;` (`direction.rgba[0..2]` replacing `real x, y, z`) supplies the missing
16-byte home with the dead fourth member at -0x30.

- `e5_probe.c` = w1's `v4c_probe.c` + do-while + aggregate -> **size 2192 and 36 relocations, both exact** (from
  2640/36), 737 vs 739 instructions, 91 differing blocks (w1's best, `pp_ish.c`, had 103).
- A third byte-proven fact (A27 fall-through polarity): January emits `jae 0x3e; and edi,0xfffe; jmp 0x42` at +0x34, so the
  then-arm is the `<` case - `if (colors[i].rgba[S3TC_ALPHA] < alpha_key) { wAlpha &= ~1; } else { wAlpha |= 1;
  cOpaque++; }`. `e7_probe.c` applies it: 2192/36 with **89** differing blocks.
- House-rule-admissible subset on its own (`e6.c` = real file + do-while + aggregate, no original forms): **2224 / 37**.
  Closer in size but one relocation over, because our plain `if (len2 == 0.0f)` lets VC7 cross-jump two `AllSame` tails at
  HEAD and the do-while breaks that merge.

Exactness still needs the three original forms, all re-confirmed in the target bytes this wave and all prohibited:

- (a) `long axis;` uninitialised - +0x5a7 `mov ecx,[ebp+0xc]` on the `m[0][0] <= 0` path; an uninitialised read feeding an
  out-of-range `m[0][axis]` index;
- (b) `if (len2 == 0.0f && cOpaque == 16)` - the target has `fld [ebp-0xc]; fcomp __real@00000000; fnstsw ax;
  test ah,0x44; jp 0x755; cmp ebx,0x10; je 0x592` at +0x73c..+0x74f (`ebx` is `cOpaque`, loaded at +0x6ec and pushed to
  `Quantize`); the `je` is the cross-jump onto the shared `AllSame` tail that gives January three `_AllSame` relocations
  instead of four. The preserved path computes 0.0f/0.0f = NaN, `__ftol2(NaN)` = 0x80000000 and indexes
  `mapRGB3[0x80000000]` - undefined behaviour;
- (c) no `block->bitmap = 0;` before the selector loop (the loop shifts a full 32 bits, so the store is behaviour-neutral)
  - not UB, but the 2026-09-07 park criterion explicitly requires "initialize ... selector packing".

**Updated reopen criterion:** owner rulings on (a), (b) and (c). The former clause "provenance for the projection-loop
index width" is satisfied and superseded - no narrow induction variable is required.

## 3. `_DecodeBlockAlpha3__single_pixel` - one register web, A43 negative class

`short shift` alone, measured this wave on the current real file (`a1.c`, independent of the `_RGBToColor` change that
w1's `a3_sh.c` conflated), closes the size envelope: **432/1, `[sha]` only**. The first 124 instructions are then
identical. Everything that remains is one register web:

| | January | ours |
| --- | --- | --- |
| bitmap accumulator | EDX (`xor edx,edx`) | EAX (`xor eax,eax`) |
| `4*v+u` index | EAX, computed at the end of each arm | ECX, computed mid-arm |
| `color` pointer | `mov eax,[ebp+0xc]` at the join, before `shr edx,cl` | loaded last, after the table read |
| table read | `and edx,7; mov dl,[ebp+edx*2-0x10]` (index register coalesced into the loaded byte) | `and eax,7; mov dl,[ebp+eax*2-0x10]` |

The whole five-byte gap is a consequence: because our arms end with the differing `mov al,[ebx+3]` / `mov al,[ebx+6]`,
VC7 cross-jumps the trailing `shl eax,8; or eax,edx` (3+2 bytes) to the join, while January keeps a copy in each arm.
**A43 records exactly this class as a negative result.**

Shapes tried this wave (3 new; w1 had already spent 5): `a2.c` shift statement first in each arm -> 448, worse;
`a3.c` single-expression `(ab2<<16)|(ab1<<8)|ab0` -> byte-identical; `a4.c` named `word value` result local ->
byte-identical. Not proposed as a park remeasure: strictly closer but not tied to a reopen (R11), and the park text
forbids choosing a narrow width to reach the size envelope, which is `short shift`'s only justification.
