## `_get_particle_world_position`: exact scratch body, owner ruling required

### New January evidence (frame `0xc4`, offsets relative to `_code_001231f0`)

1. **The 2- and 3-marker interpolation is `point_from_parametric_line`, inlined.**
   - The code is the inline expansion of this TU's already-exact helper, applied to a `vector_from_points3d`
     delta. Its final term adds `point->y`.
   - The common subexpression dz is spilled to `[ebp-0x18]`. That lies inside a 12-byte `delta` slot
     (`[ebp-0x20..-0x14]`) that exactly accounts for the donor's frame gap (`0xb8` versus `0xc4`).
   - The earlier "y-base z quirks" are therefore the helper's own historical behavior. January applies it to
     positions and to up vectors through point/vector casts.
2. **A typo leaves `knots[1]` unset on three-marker interval one.**
   - `marker_time_index[1]` is loaded at `+0x2EA` and stays on the x87 stack.
   - Only the midpoint is stored, into `[ebp-8]` (`knots[2]`) at `+0x5C6`.
   - The source is therefore `knots[2] = marker_time_index[1]; ... knots[2] = (knots[2] - knots[0]) * 0.5f + knots[0];`.
     This is a knots[2]-for-knots[1] typo that mirrors case 0.
3. **Knot copy for more than three markers.**
   - The copy is the last statement of the four-trip marker loop. January does not use a separate loop or four
     statements, and does not bind a marker pointer.
   - Shapes measured: four statements gave 1,760 bytes; knot copy first in the loop left one register-order block;
     knot copy last is exact.
4. **Offset rows.** They need named `sine` and `cosine` reals (x87 operand-order law), with sin computed first.
   Without them, 3 blocks remain.

### Why it is not admitted

Exactness requires all three of the following:
- reading `sides[0..3]` uninitialized: no 2- or 3-marker path writes them, but the third spline call reads them;
- reading `knots[1]` uninitialized on three-marker interval one;
- point-to-vector pointer casts into the genuine helpers.

The brief forbids preserving uninitialized-read original bugs. The previous lane treated the same class as owner
rulings: the `bitmap_draw_string` NULL dereference and the `biped_check_discard` varargs mismatch.

**Reopen criterion:** an owner ruling that admits these original bugs and casts for this function, or January
evidence that 2- and 3-marker glows never reach the side spline.
