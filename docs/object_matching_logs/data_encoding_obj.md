### Residual detail

- Meaningful target code size: 295 bytes; padded section: 304 bytes.
- First normalized byte divergence: `+0x4`.
  - Target begins `push ebp; mov ebp,esp; push ebx; push esi;
    mov esi,[ebp+8]; push edi; xor edi,edi`.
  - Baseline begins `push ebp; mov ebp,esp; push ebx;
    mov ebx,[ebp+8]; push esi; xor esi,esi; push edi`.
- The target owns `state` in ESI, the returned `memory` in EDI, and
  `memory_size`/the partial-width `count` path in EBX/BX.
- The baseline owns `state` in EBX, returned `memory` in ESI, and
  `memory_size` in EDI, using EAX plus LEA for the scaled-count cases.
- The first strict relocation divergence is relocation 10: the default-case
  source-path relocation is at target `+0xA6` versus base `+0xAA`. Relocations
  11-12 inherit the four-byte drift; switch-table destinations also differ at
  relocations 15-18. Counts and relocation kinds/semantic callees agree.
- Normalized differing bytes: 114 across the 304-byte padded section.

Measured facts show matching padded size, relocation count, operations,
assertions, calls, jump-table cardinality, and behavior, but different
callee-saved register ownership, partial-width count handling, scaled-count

This residual is therefore parked as a **private register-allocation and
source-lifetime fixed point (class C)**, not accepted as matching.

## 2026-08-11 provenance breakthrough and closure

The HCEA `RELEASE_CACHE` PDB provides an exact-unique cross-build mapping for
`data_decode_memory`.  It records the cross-build parameter shape
`(data_encoding_state *state, short count, long code)` and exactly one local,
`long size`; January disassembly independently proves the argument widths.
The actual HCEA PPC body loads that uninitialized stack local on the invalid
selector path, and a later HCEA reconstruction documents the same defect.
All known January callers use only `-8`, `-4`, `-2`, or `1`.  January remains
the byte oracle, but the combined provenance made the omission evidence-backed
rather than speculative.

The reconstruction reference is
`surreptitiousresearch/halocea@0dadebb5671751b8730110f90bf6c10df5f6312c`,
`src/data_decode_memory.c`; it is corroboration only, not the byte oracle.

Removing only the fallback `memory_size = count` assignment after the fatal
assertion and `system_exit(-1)` reproduces January exactly:

- `_data_decode_memory`: 304/304 padded bytes, 19/19 relocations, normalized
  SHA-256 `eb39377415e6c3e07f763e8f0f42f6ecafaf61acc0fab30fbc06062b9dc465d8`;
- all 15 sibling functions remain strict-exact, giving 16/16 functions and
  3,296/3,296 padded function bytes;
- all 14 January-owned `.rdata` sections remain strict-exact, totaling 459
  bytes with zero relocations.

This is admitted under the original-bug policy, not as a general undefined-
behavior codegen technique.  January's otherwise anomalous post-fatal reload,
the instruction-identical October topology, the exact-unique HCEA PDB local
record, and the HCEA PPC invalid-path load corroborate the omission.
The production comment identifies the defect.  A corrected build should
initialize `memory_size` before leaving the invalid-code case; the former
defined fallback is measured above as H00 and differs in 114 normalized byte
positions despite matching size and relocation count.

Independent bounded safety variants confirm that exactness is specific to the
recovered omission: `memory_size = count` restores candidate hash
`9c154cab...` with 114 differing bytes; a zero initializer produces a
288-byte function; an explicit default zero produces 304 bytes with 94
differing positions; and an immediate `return NULL` produces 304 bytes with
166 differences.  These are documented with the complete source-shape matrix
in `research/data_decode_memory_codegen/REPORT.md`.
