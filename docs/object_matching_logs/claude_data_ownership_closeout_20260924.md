## Owner note 1: the 13 revocations come from a stale objdiff binary

`configure.py` pins `objdiff_tag = "v3.6.0"`. But canonical's
`build/tools/objdiff-cli.exe` reports **3.3.1**, downloaded 2026-09-20. The
`download_tool` rule never refreshes an existing file.

3.3.1 carries the known defect in which a `$` in MSVC literal names defeats the
relocation name test (`docs/objdiff_data_relocation_defect_20260922.md`).

A fresh worktree downloads 3.6.0:
- all 13 objects already score 100% data;
- the admission audit shows 0 revoked, 0 contradicted, 23 candidates;
- the board reads 462/833.

I did not alter the scorer or canonical. Every entry added here is correct under
both versions: under 3.6.0 its unit has no unmatched data, so the entry verifies
and credits nothing.

The same holds for the ten entries in `4a39ce0d`. Only `shell_xbox`'s grouped
entry credits anything under 3.6.0.

**Owner decision:** refresh canonical's objdiff binary to the pinned 3.6.0. That
would itself clear the three remaining data revocations, so revisit their holds
below before trusting that.

## Owner note 2: grouped entries break under 3.6.0

`apply_semantic_data_matches` compares a grouped (`members`) entry's sections
with the unit's unmatched sections *before* its "no unmatched data"
short-circuit. A grouped entry for a unit that 3.6.0 fully matches therefore
fails the build. I used only single-section entries, which are safe under both
versions; each of these objects has exactly one unmatched `.data` section.

## Method (per object)

1. **Independent COFF comparison.** January split versus rebuild,
   `coff_compare.section_info_resolved`:
   - size;
   - bytes with every relocation site zeroed;
   - every relocation's address, type and final image destination (all
     resolved to addresses, none symbolic);
   - section flags including alignment.
2. **Whole-object audit** (`scratch/lane/object_audit.py`):
   - every January-owned section, matched by any owner symbol it contains, not
     only the first;
   - every January symbol's section, offset and storage;
   - the candidate-only surplus list.
3. **Storage truth.** Every defined symbol was checked against **cachebeta.pdb
   publics** (`DIA2Dump -p`; 19,094 publics).
   - A symbol absent from the publics was file-static.
   - None of the 145 absent symbols is referenced as UNDEF by any other January
     object or by any of ours (`scratch/lane/xref_check.py`).
   - Known cross-TU symbols (`_objects_update`, `_object_new`, `_sound_classes`)
     are public, which confirms the method.
4. **Surplus.**
   - Candidate-only COMDATs are compared with January's selected copies
     (`section_infos_equal`).
   - Ordinary selected-provider pair links are run in both orders
     (`scratch/lane/provider_link.py`).
   - `object_admission_rejections.json` and `parked.json` have no entries for
     any of the 13.
5. **Functions.** `gate.py --all` strict exact for every target function.

## Owner note 3: the SDK-table precedent

objects and ui_widget_event_handler_functions both emit the three stock D3D
tables that the `rasterizer_xbox_profile` rejection cites:
- `D3DTEXTUREDIRECTENCODE`;
- `D3DSIMPLERENDERSTATEENCODE`;
- `D3DPRIMITIVETOVERTEXCOUNT`.

ui_widget's copies are byte-identical to January's selected copies (headers,
progress_bar, rasterizer_xbox_decals) with the same flags, and they pair-link in
both orders.

A census finds **54 already-Matching objects** emitting the same candidate-only
tables, including aim_assist from the previous lane. So I did not treat the
tables alone as disqualifying. The `rasterizer_xbox_profile` hold also rests on
that object's own shared-declaration debt. If the owner rules the tables
disqualifying in themselves, ui_widget_event_handler_functions and the 54 need
the same review.
