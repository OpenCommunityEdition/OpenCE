### RGBToColor and DecodeBlockRGB (coupled)

January's `RGBToColor` has a four-byte frame (`push ecx`): the word `rgb` and the `struct s3tc_color` share one slot, three bytes
are stored and the dword is copied. The Microsoft Direct3D reference rasterizer contains this body verbatim in **two** files of
the local Windows Server 2003 cache (commit `5c6fe3db`): `multimedia/directx/dxg/ref8/common/dxtn.cpp` and
`multimedia/directx/dxg/d3d/ref/rast/refs3tc.cpp` ("S3 texture compression functions"; not cited by earlier ledgers). Its order:
pick off the 5/6/5 fields into the colour, shift each primary up, replicate the high bits.

Written in that statement order (candidate `scratch/workers/s3tc/reopen_rgbtocolor.c` = current real file + this one body):

- `_RGBToColor` becomes strict exact (normalized SHA-256 `ca5bedfc...40c7`, equal to the target);
- `_DecodeBlockRGB` becomes strict exact **without any change to its body** (`fea1c6a8...3529`): VC7's `/O2` auto-inliner now
  inlines the first `RGBToColor` call into the dead `source` parameter slot and calls the second one, exactly as January. The
  09-07 "instruction selection and scheduling" classification was wrong: it was an inline boundary set by the helper body;
- `_DecodeBlockRGB__single_pixel` moves to 496 / 10 relocations (`fa5385c3...7dfb`), `_Quantize` to `57685b73...87fa` (both still
  parked; remeasure needed), siblings 12 -> 14 exact, no owner change, fake scan clean, guard passes.

**Policy disclosure.** The reference body never assigns `color.rgba[3]` before `*pcolor = color`, which is the "indeterminate alpha"
the 09-07 park told reviewers not to restore. Premise refutation offered for an owner decision: every January consumer overwrites
or ignores that byte (DecodeBlockRGB and the single-pixel decoder store 0xFF/0 into the palette alpha right after the calls; Quantize
passes the colour only to ColorToFcolor, which reads channels 0..2), the read is part of a whole-aggregate copy (a struct value is
never a trap representation, and `byte` has none), and the emitted code deterministically writes zero there. If the owner keeps the
09-07 ruling, both functions stay parked.

### DecodeBlockRGB__single_pixel

With the reference RGBToColor and January's own assertion text (`u>=0 && u<=4`, `v>=0 && v<=4`, which `docs/assertions.md` requires
verbatim), exactly one instruction differs: January clears 64 bytes (`push 0x40`) of a single output colour on a null block. The only
caller (`bitmaps.c` `bitmap_2d_get_pixel`) passes a 4-byte `pixel32`. A probe with the 64-byte clear is exact, but that path is a
buffer overrun and is not proposed.

### Quantize

After the RGBToColor fix, all inlined helper structure aligns (165/165 instructions); the remaining seven blocks interleave
`fmul wtPrimary[n]` / `fmul 1/255` with the integer bit replication of the next inlined colour. ColorToFcolor as a
`ForAllPrimaries`-style loop, `/ 255.0f` (VC7 without `/Op` folds it to `* 1/255`), and `/ 255` spellings were measured: all
exact out of line, but the Quantize schedule only shuffles (a spelling lottery), so work stopped.

### DecodeBlockAlpha3__single_pixel

January computes the selector shift from the raw incoming dword slots (`mov ecx,[ebp+0x10]`, `lea eax,[ecx+edi*4]`) while still
comparing `cmp di,2`. VC7 omits the short-to-int sign extensions only when the arithmetic result is itself 16-bit: declaring the
shift count `short` (u/v stay `short`, keeping the source-backed signature) closes the size envelope, 448 -> 432, 152 vs 155
instructions. `word` is identical; `byte`, a per-arm `short pixel` with `3 * pixel` in the join, split shift statements and an
index local are identical or worse. Remaining: bitmap accumulator EDX (January) vs EAX, `lea` placement and the colour reload
before the shift. Best scratch body: `scratch/workers/s3tc/a3_sh.c`. This satisfies the promotion half of the park's reopen criterion.

### EncodeBlockRGBColorKey

Exactness needs three target-proven original forms that policy or the 09-07 park rule out:

1. `axis` uninitialised (+0x5a7 loads an arbitrary value on the `m[0][0] <= 0` path; reachable only with NaN);
2. `if (len2 == 0.0f && cOpaque == 16) AllSame(...)` (+0x74c): a colour-keyed block whose opaque texels quantise to one RGB565 value
   continues with `t = 0/0`, `(long)NaN` and a `mapRGB3[0x80000000]` index;
3. no `block->bitmap = 0` before the selector loop (the previous value is shifted out).

The 448-byte structural gap is **not** caused by those forms. It is the projection (min/max) loop: January keeps it as a plain
16-trip loop while unrolling the mean, centring and covariance loops 8x2; our `long` index unrolls it (about +154 instructions).
New measured VC7 13.00.9254 law: **a constant-trip `for` loop whose induction variable is `short` or `byte` is not unrolled;
`long` and `unsigned long` are.** Narrowing only that loop's index gives 2176 bytes / 735 instructions (target 2192/739); narrowing
every index removes every unroll (1504 bytes). Body spellings (continue, comma increment, scoped `t`, split division, product order,
accumulation, aggregate axis) and function-budget probes were inert. With no provenance for which narrow variable January used,
no source is proposed.
