# Product Guidelines: OpenCE (macOS)

## Faithfulness to the Original
- The stock game is the reference: its look, feel and behaviour stay unchanged by default.
- Anything that departs from it (ray-traced lighting, high-res HUD, extended physics) is a **setting, off or stock by default**, unless the project decides otherwise.
- Menus keep matching Halo Custom Edition's; menu XML is generated by `tools/ce_menus.py` / `tools/port_settings.py`, never edited by hand.
- **Native engine, decided 2026-10-21:** lighting and shading are enhanced only: physically based shading, re-baked bounced light, ambient occlusion, reflections and dynamic shadows replace the stock look, with no "original" mode. The goal is still the original in spirit: the same light colours, mood and readability.
- **Native engine:** the menus are the Xbox game's own UI, read from the user's `ui.map` and drawn at native resolution with mouse support. The launcher shows only Play, Settings and Exit. The Custom Edition XML rule above applies to the VM port.

## The Game's Sources (`source/`)
- Change as little as possible. Mark every change with a comment starting `port:`.
- Original bugs marked `BUG (original, ...)` may be fixed; say so in the `port:` comment.
- Port functions the game calls are declared in `halo_linux_source_fixups.h` (or included with a note naming the file).
- C stays C89 (`gnu89`): declarations before statements.

## New Code (Swift, Rust)
- **Swift** owns the app shell, windowing, input, lifecycle and the Metal renderer. Follow the Swift API Design Guidelines.
- **Rust** owns low-level logic behind a UniFFI boundary. Keep `unsafe` small, documented and next to the C FFI. Keep Rust crates free of macOS-only APIs where practical, so a wasm32 target stays possible.
- Interfaces between C, Rust and Swift are narrow, explicit and documented at the boundary.
- Write like the surrounding code: its naming, comment density and idiom.

## Performance
- Targets: 4K at 120fps+ on Apple Silicon. Treat frame-time regressions as bugs.
- Measure before and after any renderer or hot-path change (Metal frame capture, Instruments, the `--profile` build).
- Keep the simulation deterministic. Use the vendored musl maths (`halo_math.h`), never the system's, and compile without fused multiply-add.

## Writing Style (docs, comments, commits)
- Plain, descriptive English. Say what something is and does; avoid marketing words.
- Commit subjects are plain sentences saying what changed. The body says why and what was checked.
- PRs are merged with a merge commit. Follow-up commits end their subject with `(#N)`.
- Raise `HALO_PORT_NETWORK_VERSION` for any change to what machines send each other, and say why.

## Legal, Art and Credit
- The repository is CC0. Game data is supplied by the user and is never shipped.
- Never read or copy the Xbox SDK headers. GPL code (OpenSauce, Reclaimer) may be read as format documentation only, never copied.
- Decompilations of later Halo engines (for the parked physics work) are reference only, under the same rule, until their licence is checked.
- Replacement art is hand-drawn redraws. Exceptions are listed in `NON_HANDDRAWN.md`. Fonts: Overpass and OpenCE only.
- Vendored code goes in `port/third_party/<name>`, unchanged, with a README naming upstream, version and checksum.

## Untrusted Input
- Map files, mods and network packets are untrusted. Read them through bounds-checked readers and check sizes, indices and rates.
